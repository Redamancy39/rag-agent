# 切块质量检查说明

当前阶段建议先抽查切块质量，再继续做问答接口。RAG 的回答质量很大程度取决于入库文本是否保留了完整语义、单位、页码和表格来源。

## 1. 在前端检查

1. 启动后端和前端。
2. 登录后进入首页。
3. 点击左侧「文档列表」，滚动到最近入库文档表格。
4. 对 `indexed` 状态的文档点击「查看」。
5. 在弹窗里抽查切块内容、页码、表格序号和 `chunk_type`。

如果按钮不可点，通常表示该文档还不是 `indexed` 状态，或者入库失败。

## 2. 重点看什么

好的国标类 PDF 切块应尽量包含：

- 来源文件名。
- 页码，例如第 5 页。
- 内容类型，例如 `page_text`、`table_markdown`、`table_row_fact`。
- 食品类别、项目名称、限量值、单位。
- 表格行转写后的自然语言事实。

表格型内容尤其要看 `table_row_fact`。理想效果类似：

```text
来源文件：GB 2762-2025 食品中污染物限量.pdf
页码：第 12 页
内容类型：table_row_fact
某污染物在某食品类别中的限量为 0.5 mg/kg。
```

## 3. 常见问题

- `chunk_count` 明显偏低：可能是扫描版 PDF、加密 PDF、文字提取失败，通常需要 OCR。
- 切块只有标题或页眉页脚：说明正文提取质量不好，后续问答容易找不到答案。
- 表格行被拆散：如果食品类别、限量值和单位不在同一个切块里，问答准确率会下降。
- 没有页码：后续引用来源会变弱，需要检查 loader 的 metadata。
- 大量乱码或重复页眉：需要在 PDF 预处理阶段清洗。

## 5. 下一步建议

建议先抽查 6 个成功文档，每个文档看 5-10 个切块：

- 如果文本型 PDF 的页码和正文正常，可以继续做阶段 3 的检索问答。
- 如果表格型 PDF 的 `table_row_fact` 不够准，应先增强表格转写规则或引入 OCR/LLM 预处理。
- 对扫描版 PDF，再接入 PaddleOCR 作为 fallback，不要让它阻塞普通文本 PDF 的 RAG 主流程。

## 6. 问答闭环判断

前端“查看切块”展示的是写入 ChromaDB 的文本和 metadata，不是高维向量本身。真正的 embedding 是内部数字向量，不适合直接展示。

判断效果时更建议使用“问答测试”：

1. 选择一个 `indexed` 文档。
2. 输入一个能在该文档中找到答案的问题。
3. 查看回答是否为 `未找到相关答案。`。
4. 查看引用片段是否可读、是否包含答案所需数值和单位。

如果引用片段有大量 `/G21`、`/GAF` 这类编码残留，系统会把它当成不可靠证据过滤掉，避免大模型根据乱码或常识瞎答。此类 PDF 应优先用 OCR 或更强的版式解析重新入库。

对于 `GB 10766-2021 较大婴儿配方食品.pdf` 这类文件，PDF 视觉层可读，但文本层包含自定义字体编码。修复后，上传阶段会检测这类不可读文本；开启 OCR fallback 后会用 `ocr_page_text` 重新入库。
