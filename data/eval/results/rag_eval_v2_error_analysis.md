# RAG Eval v2 错误分析

评测文件：`rag_eval_v2_final.json`  
测试集：`rag_testset_v2.json`  
结果：398 / 500，通过率 79.60%

## 总体判断

当前 79.60% 不能简单理解为“RAG 链路只有八成准确”。102 个失败中，有相当一部分属于评测规则过严或测试集设计问题，尤其是 citation 关键词和同义表述匹配。

| 类型 | 数量 | 说明 |
|---|---:|---|
| 正例被模型判为未找到，但检索已有部分相关证据 | 37 | 多为证据不完整、上下文冲突或 LLM 严格拒答 |
| 仅 citation 关键词缺失 | 27 | 答案通常正确，但引用没有包含预期标准号、表号或条款号 |

## 主要原因

### 1. GB 2760 测试题存在结构性歧义

batch01 是最大失败来源。很多题只问“食品分类号 xx 对应的最大使用量或备注是什么”，但 GB 2760 表 A.1 中同一个食品分类号会在不同添加剂条目下重复出现，对应不同最大使用量。

例如 06.11 可以对应不同添加剂的 5.0 g/kg、0.3 g/kg、10.0 g/kg 等。系统召回多个相关证据后，模型无法确认用户到底问哪个添加剂，按当前严谨策略返回或接近“未找到”是合理的。

这类问题应该修改为“添加剂名称 + 食品分类号 + 食品类别”的三元约束题，否则测试集本身会偏难且不符合真实问法。

### 2. citation 判分过严

27 个失败只缺 citation keyword。常见情况是模型回答正确，也引用了文件和页码，但没有输出 expected 中的条款号，例如 `3.4.2`，或没有同时输出上游产品标准号。

这类失败更像评测脚本问题，不一定是 RAG 答错。建议 citation 评分分两级：

- 必须命中文档来源，例如标准号或文件名；
- 表号/条款号作为加分项或 warning，不直接判 fail。

### 3. expected keywords 过细或过多

部分定义题要求完整列出所有细分类，如冷冻饮品题要求同时包含冰淇淋、雪糕、雪泥、冰棍、甜味冰、食用冰等。模型答案语义正确但少列一两个词就会 fail。

这类题适合设置为“核心关键词必须命中 + 扩展关键词至少命中 N 个”，而不是所有关键词全量命中。

### 4. 跨文档题仍是当前链路短板

batch06 跨文档题常见问题是：模型能从下游通用标准 GB 2762/GB 2761 找到限量值，但没有完整引用上游产品标准，例如 GB 2712、GB 2717、GB 2718。

这说明当前检索是“并列召回”，还不是稳定的链式检索。后续应做两步检索：

1. 先从产品标准中识别引用关系；
2. 再带着食品类别/污染物/添加剂条件去通用标准中查数值。

### 5. 负例集中暴露了“部分可答时应该拒答”的问题

40 个负例中有 3 个误答。典型情况是问题包含两个子问题，其中一个可由库内证据回答，另一个需要外部解释或原因分析。模型给出了部分答案，没有严格返回未找到。

这需要在 prompt 或后处理里强化：只要问题中任一关键子问没有证据支持，就应整体 `found=false` 或明确“部分找到”，评测时单独处理。

## 下一步建议

优先级建议：

1. 修正 batch01 的 GB 2760 题目生成逻辑，把“食品分类号”题改成“添加剂名 + 食品分类号 + 食品类别”题。
2. 调整评测脚本，citation 缺条款号不要直接判 fail，改为 warning。
3. 支持 expected keyword 分组，例如 `required_keywords` 和 `optional_keywords`。
4. 为跨文档题实现链式检索或至少做 query rewrite，让问题拆成“引用标准识别”和“限量查询”两步。
5. 增强拒答策略：多子问题中只要关键部分无证据，不能用部分证据生成完整结论。

如果只看“答案明显错误/未找到/负例误答”的问题，真实 RAG 链路的主要短板集中在 GB 2760 长表格和 batch06 跨文档链路，而不是全部 102 个失败都代表系统能力不足。
